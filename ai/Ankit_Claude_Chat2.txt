What is the fundamental difference between lcoal mode and recursive mode

The fundamental difference is **where the answer comes from** — and that single difference changes what you're actually measuring when you benchmark.

## Local mode

The answer is in **your own process memory**. The resolver has a hardcoded table (`local_zone[]`) of about 8 names mapped to IPs. When a query arrives:

```
query in → parse → table lookup → build response → send
```

No network calls. No cache lookups that could miss. No upstream servers. Everything happens inside the resolver's own address space, on the same CPU core, with no I/O waits.

**Typical latency: tens of microseconds.** You're measuring your code — parsing, event loop overhead, syscall cost.

## Recursive mode

The answer comes from **the real DNS hierarchy on the public internet**. When a query arrives:

```
query in → parse → cache check → (miss) → send query to root server → wait for reply
                                        → send query to .com TLD server → wait for reply
                                        → send query to authoritative server → wait for reply
                                        → cache the answer → build response → send
```

Each of those "wait for reply" steps is a network round trip over the real internet. The resolver sits idle during each one, waiting for `epoll_wait` to fire.

**Typical latency: 50–500 ms for a cold query, under 1 ms for a cache hit.** You're mostly measuring the internet, not your code.

## Why this matters for your project

The problem statement asks you to compare AF_XDP vs ordinary UDP sockets on **latency, throughput, and CPU overhead**. AF_XDP saves microseconds per packet by skipping kernel socket layers. That saving is only visible if the rest of the pipeline is also measured in microseconds.

- **Benchmark in local mode.** Everything the resolver does is CPU-bound and sub-millisecond. Replacing UDP sockets with AF_XDP will produce a visible, measurable difference.
- **Functional testing in recursive mode.** This proves your resolver actually works — can walk the hierarchy, follow referrals, handle CNAMEs. But as the README of the baseline already noted, latency to 8.8.8.8 (~17 ms) completely drowns out any socket-layer savings.

Think of it this way: if your car has a faster engine but you're stuck in traffic, the lap time looks the same. Local mode is the empty track where the engine upgrade actually shows up.

## One more subtle difference

In local mode, the `--local` flag also tells the main loop to use `epoll_wait(timeout = -1)` (block forever until a packet arrives) instead of the 100ms poll it uses in recursive mode. Recursive mode needs the poll so it can wake up periodically to check for timed-out upstream queries. Local mode has no upstream queries, so no timeouts to track, so no reason to wake up. That's a small but real efficiency difference — one less thing between a packet arriving and the response going out.

## The missing top layer: recursive DNS resolver design

**The mental model (layer 1).** A recursive resolver is the server that does the legwork. A client (your laptop's stub resolver) asks it one question — "A record for www.example.com?" — and expects one final answer. The resolver earns that answer by asking a *chain* of other servers, none of which knows the whole answer, each of which knows only who to ask next. Contrast it with the three things it is *not*: an **authoritative server** (knows one zone cold, e.g. the .com servers), a **forwarder** (just hands your question to another recursive resolver — this is what your teammates' baseline actually is), and a **stub resolver** (the thin client library that asks a recursive resolver and does no walking).

One naming trap worth clearing up now, because it confused the earlier discussion: the service is **recursive** (client asks once, gets the final answer), but the internal method is **iterative** (the resolver itself walks the tree one hop at a time instead of delegating). Your program is "a recursive resolver that resolves iteratively." Both words are correct and they describe different things — the interface vs. the algorithm.

**The walk (layer 2).** The namespace is a tree: root (`.`) → TLD (`.com`) → authoritative (`example.com`). Each level knows only the delegation to the next level down. You bootstrap knowing exactly one thing: the 13 root server IPs, hardcoded (these are the "root hints" — the `ROOT_SERVERS[]` array in your code). The walk for www.example.com:

- Ask a **root** server for www.example.com. It doesn't know, but replies: "I don't have the answer; ask the .com servers — and here are their IPs." That reply is a **referral**.
- Ask a **.com** server the same question. Another referral: "ask example.com's servers, here are their IPs."
- Ask an **example.com** server. It's **authoritative** for that zone, so it returns the actual answer with the AA (authoritative answer) bit set.

**The sub-concepts that make the walk real (still layer 2, bleeding into 3):**

- **Referral** = a reply with zero answer records but NS records in the *authority* section pointing one level down.
- **Glue** = the A records for those NS names, included in the *additional* section. Without glue you'd have a chicken-and-egg problem (to find example.com you must contact ns1.example.com, whose address is... inside example.com). A delegation without glue is **glueless**, and then you must pause the current query and spin up a *sub-query* to resolve the nameserver's own name first. Your code handles the glue case and honestly stubs the glueless case — that's a real gap to discuss, not hide.
- **CNAME** = an alias. You asked for the A record of a name that turns out to be "really called" something else; you must restart the walk for the target name. (Your `handle_ns_response` CNAME branch.)
- **Negative answers**: **NXDOMAIN** (the name does not exist anywhere) vs. **NODATA** (the name exists but has no record of the type you asked). These are different and clients care about the difference.
- **Caching with TTL**: every record carries a time-to-live; you cache answers *and* referrals *and* negatives, keyed by (name, type), and serve from cache until expiry. This is not an optimization bolted on the side — it's what separates a resolver from a thing that hammers the root servers on every query. It's also the single biggest reason the resolver and the forwarder will benchmark completely differently.
- **Robustness**: multiple nameservers per level (so you retry a different one on timeout), a per-hop timeout, and a depth/loop budget so a malicious or broken delegation can't make you walk forever.
- **Security**: randomized transaction IDs *and* randomized source ports (defense against the Kaminsky cache-poisoning attack), plus **bailiwick checking** — only accept records a server is actually authorized to give. A .com server must not be allowed to hand you an A record for google.com and have you cache it. Your code randomizes TXIDs and checks the sender IP, but doesn't yet randomize source port (single socket) or do bailiwick checks. Both are worth naming as deliberate, documented gaps.

Why does this help?

The CPU's Translation Lookaside Buffer (TLB) caches virtual-to-physical address translations.

If packet processing frequently accesses many different memory locations, fewer page translations can reduce TLB pressure.

Huge pages aren't required for AF_XDP zero-copy.

Without this mechanism, the application might perform unnecessary system calls even when the driver is already processing TX work.

Imagine processing 100,000 packets.

Without conditional wakeups, you might make a system call for every batch even when the driver is already running.

With XDP_USE_NEED_WAKEUP, you issue a system call only when the kernel indicates that it needs one.

This can reduce system-call overhead and improve performance.

What about poll()?
The kernel documentation also allows using poll() to wake the driver in the relevant AF_XDP wakeup scenarios.

However, understand that poll() has two roles depending on the situation:

Waiting for socket readiness.

Participating in the explicit wakeup mechanism when required.

It is not correct to assume that simply calling poll() unconditionally means all submitted TX descriptors are automatically kicked.

For a straightforward implementation, use the documented sendto() pattern with xsk_ring_prod__needs_wakeup().

For the FILL ring, there is a similar consideration: when the kernel needs to be woken to replenish hardware receive buffers, userspace can submit buffers and call poll() as required.

The kernel documentation explicitly recommends enabling XDP_USE_NEED_WAKEUP for many applications because it can reduce unnecessary system calls.

6. The complete runtime loop — putting everything together
Now let's combine the five sub-steps into one event loop.

There is one important improvement over your original pseudocode: we need to manage a free-frame pool explicitly.

Otherwise, we risk:

Reusing a buffer still owned by the NIC.

Reusing a buffer still being transmitted.

Running out of receive buffers.

Losing track of frames after TX completion.

Meaning

h_proto = htons(ETH_P_IP);
Here, htons() converts a host-order integer to network byte order.

Why do we swap MAC addresses?
Suppose the incoming packet is:

Source MAC:      AA:AA:AA:AA:AA:AA
Destination MAC: BB:BB:BB:BB:BB:BB
If the DNS server is replying directly to the same client on the same Ethernet link:

Outgoing:

Source MAC:      BB:BB:BB:BB:BB:BB
Destination MAC: AA:AA:AA:AA:AA:AA
In C:

memcpy(tmp, eth->h_source, ETH_ALEN);

memcpy(eth->h_source, eth->h_dest, ETH_ALEN);
memcpy(eth->h_dest, tmp, ETH_ALEN);
But remember an important networking detail: this is valid only when the original source MAC is the correct next-hop destination for the response.

If the client is behind a router, the original destination MAC may belong to the router, not the DNS server. You must perform route/next-hop resolution rather than blindly swapping MACs.

A2. IPv4 header
The Linux kernel provides:

struct iphdr {
    __u8  ihl:4;
    __u8  version:4;
    __u8  tos;
    __be16 tot_len;
    __be16 id;
    __be16 frag_off;
    __u8  ttl;
    __u8  protocol;
    __sum16 check;
    __be32 saddr;
    __be32 daddr;
};
The bitfield ordering shown is the Linux convention; wire-format parsing should always use the correct platform definitions and network byte order.

For our response:

Incoming:
    Source IP      = 192.0.2.10
    Destination IP = 198.51.100.53

Outgoing:
    Source IP      = 198.51.100.53
    Destination IP = 192.0.2.10
In C:

__be32 temp = ip->saddr;
ip->saddr = ip->daddr;
ip->daddr = temp;
But swapping the addresses is not enough.

You must update:

tot_len if the response has a different size.

ttl according to your outgoing packet policy.

check, the IPv4 header checksum.

The IPv4 header checksum is calculated over the entire IPv4 header, including options if present.

Conceptually:

function ipv4_checksum(ip_header, ihl):

    checksum = 0

    for each 16-bit word in IPv4 header:
        checksum += word

    fold carries into lower 16 bits

    return one's_complement(checksum)
The checksum field must be zeroed before computing the new checksum.

A3. UDP header
Linux provides:

struct udphdr {
    __be16 source;
    __be16 dest;
    __be16 len;
    __sum16 check;
};
Incoming:

Source port      = 53000
Destination port = 53
Outgoing:

Source port      = 53
Destination port = 53000
In C:

__be16 temp = udp->source;

udp->source = udp->dest;
udp->dest = temp;
Then:

udp->len = htons(sizeof(struct udphdr) + dns_response_len);
Is the UDP checksum optional?
For IPv4, yes.

You can set:

udp->check = 0;
This indicates that no UDP checksum is supplied for an IPv4 UDP datagram.

However:

IPv6 UDP generally requires a checksum.

If you choose to calculate an IPv4 UDP checksum, it includes the pseudo-header.

The pseudo-header includes source IP, destination IP, protocol and UDP length.

If you change IP addresses or UDP length, the old checksum is no longer valid.

For your initial IPv4-only implementation, setting the UDP checksum to zero is a reasonable simplification.

A4. DNS message
This is where your existing resolver code becomes valuable.

Your DNS logic can be separated from the networking layer.

DNS module:

    parse_dns_name()
    parse_dns_header()
    parse_dns_question()
    cache_lookup()
    resolve_upstream()
    build_response()
These functions should ideally operate on DNS message buffers and lengths, without depending on whether the message arrived through a normal UDP socket or AF_XDP.

For example:

uint8_t *dns_message = udp_start + sizeof(struct udphdr);

size_t dns_length =
    ntohs(udp->len) - sizeof(struct udphdr);

struct dns_response response =
    build_response(dns_message, dns_length);
The DNS module doesn't need to know whether the packet came from:

A conventional UDP socket using recvfrom().

An AF_XDP RX ring.

A test file containing a DNS message.

That is good modular design.

The key insight: You can reuse your DNS parser and response builder, but you must replace the normal socket's transport handling with your own packet framing, routing, checksum, and TX handling.

Block B — The descriptor: the pivot of AF_XDP
This is arguably the most important structure in the entire AF_XDP architecture.

struct xdp_desc {
    __u64 addr;
    __u32 len;
    __u32 options;
};
Let's understand why these three fields exist.

Suppose our packet is stored in UMEM:

UMEM base address = 0x10000000

Frame 0: offset 0
Frame 1: offset 2048
Frame 2: offset 4096
Frame 3: offset 6144
A DNS query lands in Frame 1.

The descriptor is:

struct xdp_desc desc = {
    .addr = 2048,
    .len = 71,
    .options = 0
};
What does it mean?

addr = 2048
    The packet begins at UMEM offset 2048.

len = 71
    The packet occupies 71 bytes.

options = 0
    No special descriptor options are set.
The actual memory address used by the application is:

uint8_t *packet = umem_area + desc.addr;
Conceptually:

UMEM base
    |
    v
0x10000000
    |
    | + 2048
    v
0x10000800
    |
    v
+---------------------------------+
| Ethernet | IP | UDP | DNS        |
+---------------------------------+
|<------------ 71 bytes --------->|
The descriptor is only 16 bytes. The packet is 71 bytes.

The application does not receive a 71-byte copy through the RX ring. It receives a small descriptor telling it where the 71 bytes already reside.

B1. Why do RX/TX need len, but FILL/COMPLETION don't?
This is a very good conceptual question.

Think about the purpose of each ring.

Ring

What it communicates

Why length?

FILL

Here is an available buffer

No packet exists in it yet

RX

Here is a received packet

Must tell userspace how many bytes to parse

TX

Here is a packet to transmit

Must tell the driver how many bytes to transmit

COMPLETION

This TX buffer is available again

Only its address is needed to reclaim it

Let's consider each one.

FILL ring

Userspace says:

Kernel/driver:
You may use the buffer at offset 2048.
The kernel doesn't need a packet length because the buffer is empty and its capacity/layout is already known.

RX ring

After reception:

Kernel/driver:
I placed a packet at offset 2048.
It occupies 71 bytes.
Userspace needs the length because a frame might contain 71 bytes, 512 bytes, or 1500 bytes.

TX ring

Userspace says:

Kernel/driver:
Transmit the packet at offset 4096.
It occupies 87 bytes.
The driver needs the length to know what portion of the buffer to transmit.

COMPLETION ring

The driver says:

Userspace:
Transmission processing is complete.
You can reclaim the buffer at offset 4096.
The application already knows the buffer's capacity and doesn't need the old packet's length to recycle it.

Remember this rule

RX/TX = address + length
FILL/COMPLETION = address only
This describes the normal AF_XDP ring entry formats.

Block C — UMEM addressing and headroom
Now let's understand the relationship between:

Frame index

Frame size

UMEM offset

Headroom

Actual pointer

C1. Calculating the UMEM size
Suppose:

#define FRAME_SIZE  2048
#define NUM_FRAMES  4096
Then:

\[ \text{UMEM size} = 2048 \times 4096 \]
\[ = 8,388,608\text{ bytes}=8\text{ MiB} \]
The UMEM allocation is one contiguous memory region from the application's perspective.

void *umem_area = aligned_alloc(4096, 8 * 1024 * 1024);
This is illustrative allocation code. A real implementation must satisfy the alignment and size requirements of its selected UMEM configuration.

The frames are logical chunks within this region.

C2. Frame index to offset
Suppose you want Frame 3.

Frame size = 2048
Frame index = 3
Then:

\[ \text{offset}=3\times2048=6144 \]
The corresponding pointer is:

uint8_t *frame = (uint8_t *)umem_area + 6144;
This is a virtual-memory pointer.

The important distinction:

6144
    = offset within UMEM

umem_area + 6144
    = actual userspace virtual pointer
AF_XDP descriptors normally use UMEM-relative addresses, not raw userspace pointers.

C3. What does xsk_umem__get_data() do?
The libbpf helper is essentially:

static inline void *
xsk_umem__get_data(void *umem_area, __u64 addr)
{
    return (__u8 *)umem_area + addr;
}
Usage:

void *packet = xsk_umem__get_data(
    umem_area,
    desc->addr
);
You can then interpret it as packet bytes:

struct ethhdr *eth = packet;
And calculate the next header:

struct iphdr *ip =
    (struct iphdr *)((uint8_t *)packet +
                     sizeof(struct ethhdr));
This is only valid after checking that enough bytes exist for each header.

C4. Headroom — Why do we need it?
This is a subtle but important memory-management concept.

Suppose you have a packet buffer:

Frame:
+------------------------------------------------+
| Packet data                                    |
+------------------------------------------------+
Now suppose you want to prepend a new header.

If there is no space before the packet, you may have to move the entire payload to make room.

That means copying bytes.

Instead, reserve some space before the packet data:

Frame:
+--------------------+---------------------------+
| HEADROOM           | PACKET DATA               |
|                    | Ethernet | IP | UDP | DNS |
+--------------------+---------------------------+
For example:

Frame size = 2048 bytes
Headroom = 256 bytes
Available packet capacity = 1792 bytes
If the packet starts at offset 256 relative to the frame, you can prepend data by moving the logical packet start backwards into the reserved space.

Conceptually:

Before:

[ HEADROOM: 256 bytes ][ DNS payload ]

After prepending headers:

[ Ethernet ][ IP ][ UDP ][ DNS payload ]
The important detail is that headroom is not necessarily part of the packet's reported length.

One important AF_XDP addressing nuance
Don't blindly assume that every descriptor address is:

frame_index * frame_size + headroom
The actual address depends on how the UMEM is configured and how the frame is supplied and consumed.

In particular:

UMEM has a configured headroom.

The kernel/driver observes the AF_XDP headroom convention.

FILL addresses and RX descriptor addresses must be interpreted according to that convention.

xsk_umem__get_data() simply adds the supplied address to the UMEM base. It does not automatically add another headroom offset.

This distinction matters because accidentally adding headroom twice shifts your packet pointer and causes incorrect header parsing.

Also, headroom is not a magic way to avoid copying when a response is larger than a query. It gives space to prepend headers to an existing payload. If the DNS response itself is larger, you may need a separate buffer or construct the response elsewhere.

For a DNS resolver, the simplest approach is usually to build the response in a separate TX frame rather than modifying the original RX frame.

Block D — Ring mechanics: producer and consumer indices
Now we're getting into the actual mechanics behind AF_XDP.

Each ring is a circular buffer with:

An array of entries.

A producer index.

A consumer index.

A finite capacity.

Let's build one ourselves conceptually.

D1. A ring of size 4
Ring capacity = 4

Slot:     0       1       2       3
       +-------+-------+-------+-------+
       |       |       |       |       |
       +-------+-------+-------+-------+

Producer index = 0
Consumer index = 0
The ring is empty because:

\[ producer=consumer \]
Now userspace publishes a buffer address:

producer = 1
consumer = 0

Slot 0 = 2048
The kernel can consume that entry.

After consuming:

producer = 1
consumer = 1
The ring becomes empty again.

D2. How do we determine empty and full?
Let:

\(P\) = producer index.

\(C\) = consumer index.

\(N\) = ring size.

Then:

\[ \text{Available entries}=P-C \]
\[ \text{Empty}\iff P=C \]
\[ \text{Full}\iff P-C=N \]
This assumes the indices are maintained using the ring's prescribed synchronization and capacity rules.

AF_XDP rings commonly use power-of-two sizes.

Suppose:

Let's examine the actual sequence.

Example: FILL ring
Userspace wants to make Frame A available.

Example: RX ring
The NIC receives the DNS query.

The kernel/driver writes:

rx_ring[0] = {
    .addr = 2048,
    .len = 71,
    .options = 0
};
Then it publishes the producer index.

Userspace reads the descriptor and advances the consumer index.

Example: TX ring
Userspace prepares a DNS response in Frame B.

tx_ring[0] = {
    .addr = 4096,
    .len = 87,
    .options = 0
};
It advances the producer index, and the kernel/driver consumes the descriptor.

Example: COMPLETION ring
After transmission processing finishes, the kernel/driver publishes the reclaimed address.

completion_ring[0] = 4096;
Userspace consumes that address and can make Frame B available for reuse.

D5. One critical implementation detail: memory barriers
You might ask:

Why can't userspace simply write a descriptor and immediately increment the producer index?

Because concurrent execution and CPU memory ordering matter.

Imagine:

Thread A: write descriptor
Thread A: update producer index

Thread B: read producer index
Thread B: read descriptor
Without the appropriate synchronization, Thread B could observe the updated index before it observes the descriptor contents.

That would be disastrous.

The producer must publish the descriptor before publishing the index. The consumer must observe the index before reading the corresponding descriptor.

The kernel's AF_XDP ring helpers and libbpf's ring APIs implement the required memory-ordering semantics.

For actual C implementation, don't manually manipulate AF_XDP ring indices unless you really understand the memory model. Use the provided helpers.

For example:

xsk_ring_prod__reserve(&tx, 1, &idx);

struct xdp_desc *desc =
    xsk_ring_prod__tx_desc(&tx, idx);

desc->addr = tx_addr;
desc->len = response_len;

xsk_ring_prod__submit(&tx, 1);
This is the kind of code you will actually encounter in an AF_XDP application.

Block E — XSKMAP: the connection between XDP and AF_XDP
This is comparatively simple, but let's understand the actual kernel objects and how userspace configures them.

E1. What is XSKMAP?
XSKMAP is a BPF map of type:

BPF_MAP_TYPE_XSKMAP
It stores AF_XDP socket references.

Conceptually:

XSKMAP

Key                 Value
--------------------------------
0                   XSK socket 0
1                   XSK socket 1
2                   XSK socket 2
3                   XSK socket 3
The key is typically a 32-bit integer. The value represents an AF_XDP socket reference managed by the kernel, not simply an arbitrary pointer to a userspace object.

E2. How do we populate it?
The userspace application:

Creates an AF_XDP socket.

Binds it to a network interface and RX queue.

Obtains its socket file descriptor.

Inserts that socket into XSKMAP.

Conceptually:

int xsk_fd = socket(AF_XDP, SOCK_RAW, 0);

/* Configure UMEM and rings, then bind socket. */

__u32 key = 0;

bpf_map_update_elem(
    xsks_map_fd,
    &key,
    &xsk_fd,
    BPF_ANY
);
Here:

xsks_map_fd is the file descriptor of the BPF map.

key identifies the map entry.

xsk_fd identifies the AF_XDP socket.

BPF_ANY allows the entry to be created or replaced.

The socket must be appropriately configured and bound before it can be used for redirection.

E3. How does XDP use the map?
In the XDP program:

return bpf_redirect_map(
    &xsks_map,
    ctx->rx_queue_index,
    XDP_PASS
);
The complete relationship:

Userspace:
    Create XSK0
       |
       v
    Bind to eth0, queue 0
       |

    Insert XSK0 into XSKMAP[0]

    Packet arrives on queue 0
       |
       v
    XDP reads rx_queue_index = 0
       |
       v
    bpf_redirect_map()
       |

    XSKMAP[0]
       |
       v
    XSK0
       |

    AF_XDP RX ring
       |

That's essentially all you need to understand about XSKMAP for this architecture.

## What it got right that most sources don't

Worth naming, because these are the non-obvious ones and you should keep them: the warning that **releasing an RX descriptor ≠ recycling its UMEM frame** (two separate operations, and conflating them is the classic AF_XDP memory bug); the correction that **TX completions ≠ the number of frames to refill into FILL** (you need a real free-frame pool, not a 1:1 assumption); the **MAC-swap caveat** that blind swapping is only valid when the source MAC is the correct next hop; and the **headroom double-add warning** on `xsk_umem__get_data`. Also correct: explicit `XDP_ZEROCOPY` fails the bind rather than silently falling back, and you should read `XDP_OPTIONS_ZEROCOPY` rather than assume you got what you asked for.

## What will actually bite you

**1. `bpf/xsk.h` does not exist on your system.** This is the one that stops your first `gcc`. The AF_XDP helper API (`xsk_umem__create`, `xsk_socket__create`, all the ring helpers) was deprecated in libbpf 1.0 and **removed** — it now lives in **libxdp**. Your WSL is Ubuntu 24.04 (I saw the bind 9.18-0ubuntu0.24.04 version earlier), which ships libbpf 1.3+. So:

```bash
sudo apt install -y libxdp-dev libbpf-dev clang llvm
```
```c
#include <xdp/xsk.h>     /* NOT <bpf/xsk.h> */
```
```bash
gcc ... -lxdp -lbpf
```

Every code snippet in that document assumes the old libbpf location. The function names are unchanged, so it's a one-line fix — but only if you know it, otherwise it reads as "the tutorial is wrong about everything."

**2. libbpf/libxdp will load its *own* XDP program and silently ignore yours.** Phase 3 sets `.libbpf_flags = 0`. With that, `xsk_socket__create` loads a built-in default XDP program onto the interface and manages its own internal xsks_map. Then Phase 4 loads *your* `xdp_kern.o` and populates *your* map — and the two fight. Symptom: packets arrive, your program's counters move or don't, and nothing ever lands in your RX ring. You need:

```c
.libbpf_flags = XSK_LIBBPF_FLAGS__INHIBIT_PROG_LOAD,
```

This also resolves the ordering contradiction in section 4.5 — it says "populate XSKMAP before attaching the program," but with `libbpf_flags = 0` a program is already attached at socket-create time, before step 4 even runs.

**3. `XDP_USE_NEED_WAKEUP` is explained but never enabled.** Phase 5D correctly teaches `xsk_ring_prod__needs_wakeup()`, but Phase 3's config is `.bind_flags = XDP_COPY`. That helper only ever returns meaningful values if you bound with the flag set:

```c
.bind_flags = XDP_COPY | XDP_USE_NEED_WAKEUP,
```

Without it, `needs_wakeup()` returns false forever, you never call `sendto()`, and your responses sit in the TX ring undelivered. Same applies on the RX side — the doc mentions FILL has a wakeup but the loop never shows it:

```c
if (xsk_ring_prod__needs_wakeup(&fill_ring))
    recvfrom(xsk_fd, NULL, 0, MSG_DONTWAIT, NULL, NULL);
```

**4. Multi-queue NICs will make it work "sometimes."** The XDP program uses `ctx->rx_queue_index` as the XSKMAP key, and you populate only key 0 with a socket bound to queue 0. If the interface has 8 RX queues, RSS spreads packets across all of them, and anything landing on queue 3 finds an empty map entry and falls through to `XDP_PASS`. You'll see maybe 1-in-8 queries reach your resolver. Pin the interface to one queue before testing:

```bash
ethtool -l eth0          # show current queue count
sudo ethtool -L eth0 combined 1
```

The doc never flags this and it's the single most common "my AF_XDP program drops packets randomly" cause.

**5. Aligned vs unaligned UMEM is gestured at but never named.** Block C correctly warns "don't assume `addr = frame_index * frame_size + headroom`" — but then doesn't explain *why*. The actual mechanism: UMEM has two modes. In **aligned** mode (default, `flags = 0`), descriptor addresses are frame-aligned and your arithmetic works. In **unaligned** mode (`XDP_UMEM_UNALIGNED_CHUNK_FLAG`), the address packs the frame index in the high bits and a byte offset in the low bits, and you must use `xsk_umem__extract_addr()` and `xsk_umem__extract_offset()`. Stay in aligned mode for this project and the warning becomes moot — but you should know which mode you're in rather than treating it as mystery.

**6. `RLIMIT_MEMLOCK`.** UMEM pages get pinned. On kernels before 5.11 (and some configurations after), you need this before any BPF or UMEM call or you get a confusing `EPERM`/`ENOMEM`:

```c
struct rlimit r = { RLIM_INFINITY, RLIM_INFINITY };
setrlimit(RLIMIT_MEMLOCK, &r);
```

**7. The two documents contradict each other on frame reuse.** The earlier walkthrough (the 4-query/3-frame one) reuses F0 for Q1's *response*. The newer one says "allocate a DIFFERENT free frame for TX" and is right — reusing the RX frame means you can't return it to FILL while the response is in flight, which with a small pool deadlocks you. Go with the newer advice. Also note the earlier doc's "3 frames" example is pedagogically fine but operationally absurd; use 4096.

## The hole neither document touches

Both docs frame the resolver as "parse query → resolve → build response → TX." That's a **forwarder or a cache-only resolver**. Your resolver is recursive — it sends its *own* queries out to root/TLD/authoritative servers and waits for replies. Neither document addresses what that does to the packet path, and it's the biggest architectural decision left:

- Your XDP program filters on `udp dst port 53`. Replies from upstream nameservers arrive with **src port 53**, dst = your ephemeral port. They won't match your filter, so they'd go up the normal stack — which may be what you want.
- If you widen the filter to catch them, you now need the full iterative state machine driven off the RX ring, and you must construct outbound queries as complete Ethernet/IP/UDP frames with correct next-hop MACs (ARP, routing) for servers that are *not* on your local link. That's genuinely hard and far beyond the project's scope.
- Also: your resolver listens on **5353**, not 53. The XDP filter in both docs says 53.

The sane design, and the one I'd defend in your report: **hybrid.** AF_XDP handles the client-facing path (queries in, responses out). Upstream queries keep using the ordinary UDP socket your `recursive_resolver.c` already has. You benchmark in `--local` mode, where there *is* no upstream traffic, so the hybrid boundary doesn't pollute the measurement. Decide this with your team before anyone writes `xdp_kern.c`, because it determines what the filter matches.

## What I'd do with this

The material's own closing advice is right and you should follow it literally: build a **receive-and-inspect program only** — UMEM, socket, minimal XDP program, XSKMAP, print `desc->addr`/`desc->len` and the Ethernet/IP/UDP fields, recycle to FILL. No DNS, no TX. That's the smallest thing that proves items 1–6 above are all configured correctly, and every one of them fails loudly in that program rather than mysteriously in a full resolver.

Before that, one command to run in WSL, because it decides whether any of this works there at all:

```bash
zcat /proc/config.gz 2>/dev/null | grep -E 'XDP_SOCKETS|CONFIG_BPF_SYSCALL' \
  || grep -E 'XDP_SOCKETS|CONFIG_BPF_SYSCALL' /boot/config-$(uname -r)
```

If `CONFIG_XDP_SOCKETS=y` isn't there, the WSL2 kernel can't do AF_XDP at all and you need a real Linux box or a proper VM — which is a scheduling problem, not a code problem, so find out now rather than in week three.
