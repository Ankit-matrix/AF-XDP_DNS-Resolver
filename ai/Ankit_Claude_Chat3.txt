**Why the shared module (1) comes first.** If each resolver has its own parser and response builder, any speed difference could come from that code instead of from AF_XDP. With one `dns.c`, the only difference between the two binaries is receive and send. Your report needs that.

**What goes into the AF_XDP resolver (5):**
- Setup: allocate UMEM, create the socket with the three flags we talked about (`INHIBIT_PROG_LOAD`, `XDP_COPY | XDP_USE_NEED_WAKEUP`, and the memlock rlimit), load the XDP program, fill the XSKMAP, then attach.
- A free-frame pool. Each response gets its own TX frame, separate from the RX frame the query arrived in.
- Turning a query into a response: swap the MAC addresses, IPs and ports, fix the lengths, recompute the IP checksum, and set the UDP checksum to 0.
- The event loop: poll → read RX → `dns.c` → TX → wake the kernel if needed → reclaim completions → refill FILL.
- `--local` mode only, which is the mode we benchmark. Recursive mode with upstream queries over a normal socket can come later, if you want it to work end to end.

**The test network (7).** `dnsperf` runs in the client namespace and both resolvers listen on the other end of the veth pair. That way both resolvers see exactly the same traffic over the same path. Two things to know:
- veth only supports copy mode, not zero-copy. That's fine, but say so in the report.
- If your teammate has a NIC that supports zero-copy (Intel i40e/ice, Mellanox mlx5) and a second machine to generate traffic, you could add a native zero-copy run as a bonus.
- Turn checksum offload off on the veth (`ethtool -K ... tx off`). Otherwise the client may reject responses whose checksums look wrong.

**Don't vendor them.** Three reasons:

1. **ABI mismatch.** `<linux/bpf.h>` and the libbpf/libxdp headers must match the kernel and the installed shared libraries (`libbpf.so`, `libxdp.so`) on the machine running the code. If you ship headers from your WSL kernel and your teammate links against their distro's `libbpf.so.1`, the struct layouts can disagree and you get silent corruption or verifier rejections. These are not portable like a pure-userspace library.

2. **Licenses.** `linux/*` headers are GPL-2.0, libbpf is LGPL-2.1, libxdp is BSD-2-clause. Vendoring them into your repo means you now have to carry their license files and respect their terms for a course submission. Not worth it.

3. **The install is one command.** The headers come from distro packages that ship the matching `.so` files alongside. That's the whole point.
