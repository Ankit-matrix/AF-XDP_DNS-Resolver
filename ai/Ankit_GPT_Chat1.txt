In AF_XDP, the standard setup has 4 rings per AF_XDP socket, not 4 rings shared across the entire application.

The four rings are:

1. RX ring – Kernel → User space: delivers received packet descriptors.
2. TX ring – User space → Kernel/NIC: sends packet descriptors for transmission.
3. FILL ring – User space → Kernel: supplies empty UMEM buffers for receiving packets.
4. COMPLETION ring – Kernel → User space: tells the application which transmitted UMEM buffers can be reused.

Important distinction: RX/TX rings belong to the socket, whereas FILL/COMPLETION rings belong to the UMEM.

For a single socket with its own UMEM:

UMEM

Packet buffer memory

FILL ring

COMPLETION ring

AF_XDP Socket

RX ring

TX ring

Example:

| Configuration                       | Total rings |
| ----------------------------------- | ----------- |
| 1 socket + 1 UMEM                   | 4           |
| 2 sockets + separate UMEMs          | 8           |
| 2 sockets + shared UMEM, same queue | 6           |
| 4 sockets + shared UMEM, same queue | 10          |

For shared UMEM on the same queue, you have one FILL and one COMPLETION ring, but each socket has its own RX and TX rings.&#x20;

Yes. In your AF_XDP DNS resolver, the RX ring receives only packets that the XDP program redirects to that particular AF_XDP socket using `XDP_REDIRECT`.

For example:

```
if (udp->dest == 53)
    return bpf_redirect_map(&xsks_map, queue_id, 0);

return XDP_PASS;
```

The flow is:

- DNS packet (UDP destination port 53): XDP redirects it → AF_XDP socket → RX ring → userspace resolver.
- Non-DNS packet: XDP returns `XDP_PASS` → continues through the normal kernel networking stack.
- Dropped packet: XDP returns `XDP_DROP` → discarded; never reaches the RX ring.

So, the RX ring is not a copy of the NIC's entire RX queue. It contains descriptors for packets successfully redirected to that AF_XDP socket.

One correction to keep in mind: the FILL ring doesn't contain the actual DNS queries. It contains addresses of available UMEM frames. The RX ring contains descriptors pointing to frames holding received packets.

## 2. Initialisation: FILL ring is populated

Before packets arrive, userspace allocates three UMEM frames and submits their addresses to the FILL ring.

```
       USERSPACE

      +----------------+
```

At this point:

- F0, F1, F2 are available for receiving packets.
- FILL ring has supplied all three addresses.
- No DNS packets have arrived yet.
- RX ring is empty.

Since all four packets are DNS queries, XDP redirects them to the AF_XDP socket.

It is not stored in the RX ring waiting for a frame.

The client may retransmit Q4 later.

This is the first important lesson: the number of frames in UMEM can limit how many packets you can receive before recycling buffers.

## 6. Userspace DNS resolver consumes the RX ring

Now the userspace application polls the RX ring.

It sees:

| RX descriptor | UMEM address | Packet |
| ------------- | ------------ | ------ |
| D1            | F0           | Q1     |
| D2            | F1           | Q2     |
| D3            | F2           | Q3     |

The application accesses the actual packet bytes using those UMEM addresses.

For each query, it:

1. Reads Ethernet, IP and UDP headers.
2. Extracts the DNS message.
3. Parses the DNS question.
4. Performs DNS resolution.
5. Constructs a DNS response.

For simplicity, assume all three queries are successfully resolved.

## 7. The resolver sends DNS responses: TX ring

Let's process Q1 first.

The application has read Q1 from F0. Once it has finished using the incoming packet data, it can reuse F0 to construct the DNS response.

```

             UMEM F0

          KERNEL / DRIVER
                 |
                 v
               NIC
                 |
                 v
          DNS CLIENT 1
```

The TX ring contains the descriptor pointing to the response in F0. The actual response bytes are still in UMEM.

The kernel/driver consumes the TX descriptor and transmits the packet.

## 8. COMPLETION ring: what happens after transmission?

Once the kernel has finished transmitting the packet, it returns the TX buffer address through the COMPLETION ring.

```
       TX RING
           |
           v
      KERNEL / NIC
           |
           | Packet transmitted
           v
   COMPLETION RING
           |
           | Returns F0
           v
       USERSPACE
           |
           v
      F0 available
```

The userspace application consumes the completion entry and regains ownership of F0.

It can now put F0's address back into the FILL ring.

```
COMPLETION RING
       |
       | F0 returned
       v
USERSPACE
       |
       | Recycles F0
       v
FILL RING
       |
       | Kernel can use F0 again
       v
UMEM
```

Important: COMPLETION is specifically for returning transmitted buffers. It does not automatically recycle received buffers. Userspace manages that process.

Remember this distinction:

- XSKMAP: maps keys to AF_XDP sockets.
- AF_XDP socket: receives and transmits packets through its rings.

Think of the XDP program as one traffic controller directing packets to multiple AF_XDP sockets.

Wont one program make it asynchronous?

No. Having one XDP program does not make the system synchronous or asynchronous. The number of XDP program instances and the concurrency of packet processing are two different things.

The important thing is that XDP executes in the NIC driver's receive-processing context, not as one continuously running application thread.

### 1. How one XDP program handles multiple packets

Suppose four DNS packets arrive:

```
          NIC RX QUEUES
          Q1 Q2 Q3 Q4
               |
               v
        +--------------+
        | XDP PROGRAM  |
        | Same program |
        +--------------+
               |
          XSKMAP lookup
          /    |    \
         v     v     v
       XSK0   XSK1  XSK2
```

The same loaded XDP program can be executed many times for different packets.

It doesn't mean one execution handles all four packets sequentially.

### 2. Where does concurrency come from?

Primarily from multiple RX queues and CPU processing.

For example:

Two RX queues, two CPUs

CPU 0

RX Queue 0

XDP execution for Q1, Q2

AF_XDP Socket 0

CPU 1

RX Queue 1

XDP execution for Q3, Q4

AF_XDP Socket 1

One attached XDP program, executed independently in different receive-processing contexts.

Both CPUs can execute the same XDP program concurrently.

### 3. What about your DNS resolver?

There are two separate stages:

| Stage                                | Concurrency                                    |
| ------------------------------------ | ---------------------------------------------- |
| XDP packet filtering and redirection | Can execute concurrently across RX queues/CPUs |
| Userspace DNS resolution             | Depends on your worker/thread architecture     |

For example, your userspace resolver could have:

- One socket and one processing thread: largely sequential processing.
- Multiple sockets and multiple worker threads: parallel processing.
- One socket with a multithreaded application: possible, but requires careful coordination around ring ownership.

The key takeaway: One XDP program does not imply one execution thread. The XDP program is shared code; multiple CPUs can execute it concurrently. Your userspace resolver's parallelism is a separate architectural decision.

In your AF_XDP DNS resolver, recursive DNS queries that your resolver sends to upstream DNS servers generally pass through the normal Linux networking stack, not through your AF_XDP RX/TX rings.

This is an important distinction because your project is replacing the networking path for DNS packets arriving at your resolver, but it doesn't automatically replace the networking path used for outgoing recursive queries.
