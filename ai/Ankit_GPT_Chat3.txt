Your teammate will probably be talking about these AF_XDP components:

| Component       | What it does                                                     |
| --------------- | ---------------------------------------------------------------- |
| XDP program     | Runs in the kernel and decides what to do with incoming packets. |
| XSKMAP          | Maps an XDP redirect to an AF_XDP socket.                        |
| UMEM            | Shared packet-buffer memory used by AF_XDP.                      |
| RX ring         | Passes received packet descriptors to userspace.                 |
| TX ring         | Passes outgoing packet descriptors for transmission.             |
| Fill ring       | Supplies available buffers for incoming packets.                 |
| Completion ring | Notifies userspace when transmitted buffers can be reused.       |

The important difference: UDP gives you DNS payloads; AF_XDP gives you packet frames.

With UDP, the kernel does much of the network-stack work for you. With AF_XDP, your userspace application takes responsibility for more of that work, including parsing headers, managing buffers, and constructing packets.

That's the actual engineering work involved. AF_XDP isn't simply another version of `recvfrom()`.

Yes. Your project is implementing a recursive DNS resolver using two different networking mechanisms: UDP and AF_XDP.

There is an important distinction:

- Recursive resolver: Takes a client's DNS query and obtains the final answer on the client's behalf.
- Iterative resolver: Queries DNS servers step by step, following referrals from root → TLD → authoritative DNS servers.

Your project description explicitly says real iterative resolver, which describes how the resolver performs upstream lookups.

### How your resolver works

Suppose a client asks for `google.com`.

1. Client sends a DNS query to your resolver.
2. Your resolver contacts a root DNS server.
3. Root server refers it to a `.com` TLD server.
4. Your resolver contacts the `.com` server.
5. TLD server refers it to Google's authoritative DNS server.
6. Your resolver contacts Google's authoritative server.
7. It obtains the IP address and returns it to the original client.

why is AF_XDP faster

AF_XDP is potentially faster because it reduces the amount of work the Linux kernel has to do for every packet and gives your userspace application more direct control over packet processing.

The biggest difference is not that AF_XDP uses a faster protocol than UDP. It is that it provides a different, more efficient packet-processing path.

Let's compare the two in the context of your DNS resolver.

## 1. UDP vs AF_XDP: What happens to a packet?

### Conventional UDP backend

When a DNS query arrives:

Incoming Ethernet packet

Linux network stack

Ethernet → IP → UDP processing

UDP socket receive buffer

Kernel queues the DNS payload

Userspace: recvfrom()

DNS application receives the payload

DNS resolution logic

The kernel performs substantial work before your application receives the DNS query.

For the response, the reverse networking path is used: your application calls `sendto()`, and the kernel processes and transmits the packet.

### AF_XDP backend

Incoming Ethernet packet

XDP program

Runs early in the kernel's receive path

XSKMAP → AF_XDP socket

Redirects packet to userspace socket

UMEM + RX ring

Userspace accesses packet buffers through descriptors

DNS resolution logic

Application parses packet headers and DNS payload

AF_XDP can redirect packets before they traverse the conventional UDP socket receive path.

This is where the performance opportunity comes from.

## 2. Five reasons AF_XDP can be faster

1\. Bypasses much of the conventional network stack

With ordinary UDP, packets go through the kernel's IP and UDP processing before reaching your socket.

AF_XDP can redirect packets at the XDP layer, avoiding much of that processing for the redirected traffic.

2\. Reduced copying

With conventional UDP, packet data is generally copied from kernel-managed packet buffers into the application's userspace buffer.

AF_XDP uses UMEM, which is shared between the kernel and userspace.

This can reduce data-copying overhead, particularly in zero-copy mode.

3\. Fewer system calls through batching

A conventional implementation might call:

```
recvfrom();
process_packet();
sendto();
```

for each packet.

AF_XDP uses rings that allow userspace to process multiple packet descriptors in batches.

Fewer system calls and better batching can improve throughput.

4\. Better memory management

AF_XDP gives your application control over packet buffers through four rings:

| Ring       | Responsibility                        |
| ---------- | ------------------------------------- |
| Fill       | Supplies buffers for incoming packets |
| RX         | Delivers received packet descriptors  |
| TX         | Queues outgoing packet descriptors    |
| Completion | Returns transmitted buffers for reuse |

This enables efficient buffer reuse and reduces allocation overhead.

5\. Better control over CPU processing

You can use dedicated queues, CPU affinity and multiple AF_XDP sockets to distribute packet processing across CPU cores.

This can improve scalability under high packet loads.

## 3. The biggest difference: Copy mode vs Zero-copy mode

Important distinction:

- AF_XDP copy mode still has packet-copy overhead.
- AF_XDP zero-copy mode can eliminate an additional packet-data copy.
- Zero-copy requires compatible NIC driver and hardware support.

Don't assume that simply using AF_XDP means you're running zero-copy.

## 4. Why this matters for your DNS project

Consider 100,000 DNS queries per second.

Your resolver needs to:

- Receive 100,000 packets.
- Parse 100,000 DNS queries.
- Perform resolution or cache lookups.
- Construct 100,000 responses.
- Transmit 100,000 packets.

Every unnecessary operation becomes significant at this scale.

AF_XDP attempts to reduce the cost of receiving and transmitting those packets.

However, there is an important catch: AF_XDP does not make DNS resolution itself faster.

If your resolver spends most of its time waiting for root, TLD or authoritative DNS servers, optimizing packet reception might have little impact on total query latency.

That's why your stub benchmark is particularly useful: it isolates networking and packet-processing overhead from external DNS lookup delays.
